- Register as a hacker. Teams may have **1–4 members**, with no more than four. Add teammates to the Devpost submission; no separate team confirmation is required.
- Start the project during the event and follow the MLH Code of Conduct.
- Submit by **Sunday, October 25, 9:00 AM Pacific / noon Eastern**. Late projects are excluded. The current Devpost deadline banner explicitly says **PDT**; older body copy still says PST. Guide venue schedule says 9 AM without a timezone. Preserve the stale-label discrepancy and follow the official event clock.
- Be in person for judging, move to the assigned table by **10:30 AM**, and remain available until **12:30 PM**. The guide requires a **live demo** and recommends a two-minute pitch.
- Include a clear video demo for sponsors evaluating asynchronously. [Organizer judging explanation](https://cal-hacks-13-0.slack.com/archives/C0C6X34TC6A/p1791857325971519).
- Devpost additionally requests a project image and GitHub code link. [Devpost requirements](https://cal-hacks-13-0.devpost.com/).
- There is **no limit** on track selections; a project may enter multiple tracks if it satisfies each sponsor's criteria. Select/tag sponsor tracks during Devpost submission. No separate advance application deadline for sponsor tracks was stated. Hardware access can have separate applications.
- Main tracks are automatically open for consideration according to organizers; this does not define the special beginner/solo category rules.
- Solo category selection is available during Devpost submission. [Solo-track reply](https://cal-hacks-13-0.slack.com/archives/C0C6X34TC6A/p1792467759602629).

Sources: [guide](https://docs.google.com/document/d/1RQrueC9wm5u8uxtWSC2gadIchp05hVayhGUrIjxT9dE/edit), [no limit and main-track eligibility](https://cal-hacks-13-0.slack.com/archives/C0C6X34TC6A/p1792716847336219), [multiple-track confirmation](https://cal-hacks-13-0.slack.com/archives/C0C6X34TC6A/p1792721198191709), [sponsor signup timing](https://cal-hacks-13-0.slack.com/archives/C0C6X34TC6A/p1792645667305779).

### S13. Best Use of Cartesia (Cartesia)

**Guide criteria / requirements:**

Build a useful voice experience with Cartesia. Voice should be core to the product–not just a feature added for the demo. Other tools are fine; make clear what Cartesia contributes.

What to submit
• A working demo
• A 2-minute, demo-first presentation: one complete user flow, then a brief problem + how you built it
• A short README: setup, Cartesia features used, known limitations
• Source access for judges (per event rules). No API keys or secrets in the repo

Judging criteria (25% each)

Problem and originality — Useful, clearly scoped, thoughtfully designed?
Use of Cartesia — Meaningfully integrated into the core experience? Voice clear, responsive, and natural?
Execution — Main flow works? Likely edge cases handled?
Impact and responsibility — Accessibility, privacy, and responsible use considered?

We’ll favor a strong working prototype over a large unfinished idea.

Ideas
• Commute standup — voice-only morning brief you can interrupt while driving (hands-busy)
• Ambient / wearable assistant — help without pulling out a phone
