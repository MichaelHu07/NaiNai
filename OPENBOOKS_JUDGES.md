## How this changes OpenBooks

These are project preparation decisions, not predictions about individual scoring.

1. **Make agent value testable beyond a duplicate rule.** Add an equal-amount/different-legitimate-claim counterexample to avoid rewarding false positives. Use exact matching/calculations for facts; let an agent interpret messy supporting documents, conflicts and missing context. Require citations and an explicit unknown when necessary.
2. **Prepare a compact investigation trace.** Show source record IDs/versions, tool calls, checks, evidence, conclusion, escalation and the human decision. Show concise actual actions and results rather than invented hidden reasoning.
3. **Make authorization and recovery visible.** Approval applies to one reviewed version; changing evidence invalidates it. Retrying or restarting must not create a second authorized result.
4. **Prepare a small known-answer evaluation.** Ordinary, duplicate, same amount but different valid claim, changed details, inconsistent document, unavailable source, stale approval and repeated request. No benchmark score is claimed until run.
5. **Preserve the adoption argument.** The specific treasurer community and real workflow evidence remain unvalidated. Prepare a short answer to who would use it next week, what it replaces, and why a human would trust it.
6. **Keep the core product intact.** These backgrounds support strengthening evidence, controls and usability. They do not justify a hardware pivot, extra agent framework or feature for every judge.

## Demo emphasis and Q&A cards

| Evidence emphasis | 15–20 second preparation card | Proof to have ready |
|---|---|---|
| Finance autonomy | “This replaces the reconciliation/investigation work while the treasurer retains approval.” | Role boundary, conflict, policy source, escalation and audit |
| Agent evaluation | “We test known outcomes, including a same-amount claim that must not be called a duplicate.” | Answer key, case results, tool/evidence trace |
| Reliability | “Changing this record invalidates its approval; retrying cannot create a second result.” | Actual stale/retry/restart check |
| Product/adoption | “The initial user is [actual community]; our observed problem was [real finding].” | Real participant notes and observed usability result; placeholders remain until obtained |
| Sponsor integration | “This provider performs [central operation], which changes [specific outcome].” | Actual operation/run link and source provenance |

Use one truthful story for every audience. Change emphasis, not evidence or claims.

Question bank to rehearse:
- Why does this require an agent rather than a spreadsheet or duplicate checker?
- Can two equal-amount claims both be legitimate?
- How do you know a citation supports the conclusion?
- Which checks are deterministic and which are uncertain?
- What prevents the model from approving its own recommendation?
- What happens if a provider times out?
- What happens if source data changes after review?
- What happens after a crash/retry?
- Who actually validated the problem, and what changed as a result?
- Which integrations are live, seeded or simulated?
- What would make the initial user adopt it?
